## 1. What it is and why

A USB-C stick that exposes an ATECC608B secure element to a computer. No microcontroller, no
firmware. The MCP2221A is a fixed-function USB-to-I2C bridge: the host enumerates it as a USB HID
device and issues I2C reads/writes through it. The ATECC608B holds a P-256 key that never leaves the
chip; the host sends a 32-byte digest, gets back a signature.

```
host USB-C receptacle ──► J1 plug ──► U1 MCP2221A ──I2C (SDA/SCL, 4.7k pull-ups)──► U2 ATECC608B
                                        │
                                   GP3 → blue LED (I2C activity)
                                   5 V from VBUS powers everything; no regulator
```

Why this shape: Austin asked for exactly this (crypto chip, I2C-to-USB bridge, USB-C male plug,
computer does the signing). It's the picowallet's secure element without the Pico, screen, buttons,
or battery. Same key-handling story, same `firmware/atecc.py` wire protocol, ported to the host.

## 3. Every design decision, with the reasoning

### 3.1 Power: everything on VBUS 5 V, no regulator
MCP2221A VDD is 3.0–5.5 V (DS20005565C, §"Electrical Characteristics"). ATECC608B VCC is 2.0–5.5 V
(DS40002239A). Both are happy at 5 V, so the 5 V from the host goes straight to both. The MCP2221A
makes its own 3.3 V for the USB transceiver internally on VUSB, which is why C1 exists. I2C runs at
VBUS level (pull-ups to VBUS); both chips' I2C pins are referenced to their own VDD/VCC, which is the
same rail. One fewer part, one fewer failure mode.

### 3.2 USB-C plug wiring (this is where the most judgement is)
A USB-C plug has 24 positions in two rows, A1–A12 (top) and B1–B12 (bottom). The host receptacle
internally ties A4/A9/B4/B9 (VBUS) together and A1/A12/B1/B12 (GND) together, and for USB 2.0 hosts
ties A6/B6 (D+) and A7/B7 (D−) together. It monitors CC1 (A5) and CC2 (B5) independently to detect
which way the plug is flipped.

**What I wired:**
- VBUS: B4, B9 (bottom row). GND: B1, B12 + the two shell/ground pads (pads 25, 26).
- D+: B6. D−: B7.
- CC: **A5** (top row) through R1 5.1 k to GND. B5 (VCONN) left open.
- A1, A4, A6, A7, A9, A12 (top-row power/data): **left open**.

**Why the top row's power and data are open:** the 0.5 mm-pitch top-row pads, sandwiched between the
plug shell pads and the bottom row, would not autoroute together with everything else; the router
gave up on 6 of them. Electrically it doesn't matter for USB 2.0 because the receptacle shorts
A-row and B-row VBUS/GND/D+/D− together; one row carries everything in either orientation. It is
not spec-exact (the spec expects both rows populated for current capacity), but at the < 100 mA this
stick draws, one VBUS pin (rated 3 A on this plug) is plenty. **Reviewer: confirm you agree this is
harmless for a USB 2.0 low-power device.**

**Why CC is on A5 and not B5:** the USB-IF Type-C Functional Test Spec says a device with a captive
plug "shall apply and sense CC voltage levels on pin A5 only and pin B5 shall have an impedance above
zOPEN". v0.1/v0.2 had Rd on B5 (wrong row). v0.3 moved it to A5. Functionally a host can't tell the
difference (plug A5 lands on host CC1 or CC2 depending on flip, and the host checks both), but A5 is
the rule and it routed fine.

**Plug pin labels vs. our net names:** the import file `imports/TYPE_C_24P_GTJB_040.tsx` labels the
pads by A/B position *and* by function; the functional aliases are inconsistent (its "CC1" is A5,
"CC2" is B5, "DP2/DN2" are B6/B7, "VBUS1/VBUS2" are B9/B4). `NETLIST.txt` shows the raw A/B names,
which is what to check against the plug drawing's pin table (`ref/…pdf` page 2, "PIN DEFINE TABLE").

### 3.3 The plug footprint, and the one hand edit
`tsci import` pulled the LCSC/EasyEDA footprint for C3151751. It came with all 24 signal pads on the
**top** layer. A clamping plug straddles the board: A-row contacts on top, B-row contacts underneath.
So I edited `imports/TYPE_C_24P_GTJB_040.tsx` to put pins 27–38 (B1–B12) and pad 25 on the bottom
layer. I also stripped its silkscreen outline and courtyard because they described the plug body,
which hangs off the board and was tripping the overlap checker. **This edit is the highest-risk
thing in the design**, see §5.1.

Pad geometry as built (from `NETLIST.txt`): 12 pads per row, 0.30 × 1.50 mm, 0.5 mm pitch, centered
at x = −13.95, spanning y = −2.75…+2.75. Board edge is at x = −15.0, so the pads run from 0.30 mm to
1.80 mm in from the edge. The plug drawing (page 2, "Cable Side PCB Layout, T=0.80±0.05mm") shows a
12×1.50 pad pattern at 0.50 pitch with a 0.90 and a 1.30 dimension near the edge that I could not
read with confidence at the resolution I had. **Reviewer: open the PDF at full size and confirm
where the pads should sit relative to the board edge.** If the drawing says pads start 0.9 mm from
the edge, we are 0.6 mm too close and `pcbX` of J1 must move from −13.95 to about −13.35 (and the
board can stay 30 mm).

### 3.4 MCP2221A wiring (checked pin by pin against DS20005565C, TSSOP-14 pinout, §1)
| Pin | Name | Ours | OK? |
|---|---|---|---|
| 1 | VDD | VBUS + C2 100 nF to GND | ✓ |
| 2 | GP0 | open | ✓ (default function SSPND/LED_URX output; unused) |
| 3 | GP1 | open | ✓ |
| 4 | RST | 10 k to VBUS | ✓ active-low reset, pulled high |
| 5 | URX | open | ✓ UART unused |
| 6 | UTX | open | ✓ |
| 7 | GP2 | open | ✓ |
| 8 | GP3 | LED2 cathode (anode via 1 k to VBUS) | ✓ see §3.5 |
| 9 | SDA | net SDA, 4.7 k to VBUS | ✓ |
| 10 | SCL | net SCL, 4.7 k to VBUS | ✓ |
| 11 | VUSB | 470 nF to GND | ✓ required |
| 12 | D− | J1 B7 | ✓ |
| 13 | D+ | J1 B6 | ✓ |
| 14 | VSS | GND | ✓ |

D+/D− polarity: verified against the plug pin table (A6/B6 = D+, A7/B7 = D−) and the MCP2221A pinout
(12 = D−, 13 = D+). Swapped D± is the classic "enumerates as nothing" bug; worth a second look.

### 3.5 The blue LED is wired "backwards" on purpose
GP3's factory-default function is LED_I2C (EasyMCP2221 docs list it as the default; DS20005565C
says the pin takes the *negated* value of the activity bit, i.e. it pulses **low** during traffic).
Microchip's ADM00559 wires its LEDs from VDD through a resistor into the GP pin. So: LED2 anode →
R6 1 k → VBUS, LED2 cathode → GP3. It lights when GP3 goes low = during I2C traffic. v0.2 had it the
other way round (would have been on at idle, blinking off). If GP3's default in this chip lot is
plain GPIO instead, the LED just stays off; Microchip's free utility can set it.

### 3.6 ATECC608B wiring (DS40002239A, SOIC-8)
Pin 4 GND, 5 SDA, 6 SCL, 8 VCC (+ C3 100 nF). Pins 1–3, 7 NC, left open. I2C address 0x60 (write
0xC0). Matches `imports/ATECC608B_SSHDA_T.tsx` and the picowallet build that already works with this
chip.

### 3.7 Board size and layout
30 × 12 × 0.8 mm, 2 layers. The left 13 mm is inside the plug shell. U1 and U2 on the front, every
passive and both LEDs on the back. Austin asked why it's this big: the honest answer is the floor is
about 26 × 10 (plug shell width 8.5, two chips 5+5 wide side by side) and I left ~4 mm of slack
around the LEDs and between the chips for routing. Making it smaller doesn't change function.
Board thickness 0.8 mm is forced by the plug (§3.2); 0.8 mm is a standard JLCPCB option.

### 3.8 Routing
Autorouted by tscircuit (2 layers, vias allowed). 37 traces, 15 vias. `check shorts` clean. Trace
width is the default 0.15 mm, which is fine for < 100 mA. The VUSB cap traces carry an explicit
`maxLength="6mm"` because the tool imposed a 1 mm rule from the chip's decoupling hint that the
layout can't meet; actual length is ~4.4 mm, well within Microchip's "close to the pin" guidance.

## 4. Things I changed my mind on (so the reviewer sees the trail)
1. **v0.1 → v0.2:** 40 × 14 → 30 × 12 mm, passives moved to the back. No electrical change.
2. **v0.2 → v0.3:** CC moved from B5 to A5 (USB-IF plug rule). LED2 inverted to match LED_I2C's
   active-low behaviour. Both routed first try.
3. **Plug pad layers:** import had all 24 on top; hand-moved the B row to bottom (§3.3).
4. **Dropped B6/B7 duplicates then re-added as the only data pins:** first attempt wired A6/A7 *and*
   B6/B7; router failed on the A row; settled on B row only.

## 5. Risks, ranked by "would this make the first board dead"
1. **Plug pad-to-edge distance (§3.3).** Unverified against the drawing. If wrong, the plug's spring
   contacts miss the pads → no power, dead stick. Fix is a number in `index.circuit.tsx`.
   **Do not order until a human has checked this.**
2. **Plug pad layer assignment (§3.3).** My hand edit assumes A row = top of board = the side the
   shell's A-row contacts touch. If the plug is meant to be mounted the other way up, A and B swap.
   Consequence: CC ends up on B5 (works anyway, see §3.2) and power/data on the A row (also works).
   So even if wrong, it probably still works. Low impact.
3. **D+/D− swap (§3.4).** Checked twice. Consequence if wrong: not enumerated.
4. **Only one plug row wired (§3.2).** Believed harmless for USB 2.0 at < 100 mA.
5. **RST pull-up (§3.4).** Present. If the chip also has an internal one, no harm.
6. **No ESD protection** on D+/D−. Bench use is fine; add a USBLC6-2SC6 in v1 before giving these to
   people.
7. **Blue LED** depends on GP3 default (§3.5). Cosmetic.
8. **JLCPCB assembly of the plug:** "high difficulty" + fixture fee; the plug is placed by the SMT
   line and the board edge slides into it. If JLCPCB refuses to place it, it's a 30-second hand job
   with the clamp, or they hand-solder it for the through-hole fee.
9. **Not electrically tested.** Passed netlist, placement and shorts checks in tscircuit only. Nobody
   has powered one. KiCad ERC/DRC on `kicad.zip` would be a cheap second check.

## 6. What "works" means on arrival (bring-up)
1. Plug in. Green LED on. `lsusb` / System Information shows "Microchip MCP2221 USB-I2C/UART Combo".
2. `pip install EasyMCP2221`, then in Python: `d = EasyMCP2221.Device(); d.I2C_speed(100000);
   d.I2C_write(0x60, b'\x00'); d.I2C_read(0x60, 4)` — an ATECC wakes on the low pulse and answers
   0x04 0x11 0x33 0x43. Blue LED flickers during this.
3. Port `firmware/atecc.py` (already speaks the ATECC wire protocol) from MicroPython `machine.I2C`
   to EasyMCP2221's `I2C_read/I2C_write`: `info`, `random`, `genkey`, `sign`.
4. Verify a signature with the same P-256 code the picowallet app uses.
